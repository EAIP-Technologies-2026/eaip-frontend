# Taste
- Works with multiple engineers in parallel and expects strict scope isolation: never touch work in progress or areas outside one's assigned responsibility (e.g., explicitly "DO NOT redesign the UI" / "DO NOT touch workflow designer"), and stop at the scope boundary rather than continuing into adjacent work. Confidence: 0.8
- Expects quality gates (`pnpm lint`, `pnpm build`) to run until clean, but only fix issues caused by one's own changes — not unrelated pre-existing problems. Confidence: 0.7
- When a runtime/diagnostic task is commissioned, expects implementation to be the SMALLEST correct fix only: no refactoring, rewriting, redesigning, new components, duplicate providers, mocks, hacks, or bypassing existing guards (e.g., `RequireAuth`) — reuse existing architecture and frozen contracts, and only repair the verified failure. Confidence: 0.9
- Expects runtime verification to be evidence-driven: trace the full lifecycle end-to-end (start backend + frontends, verify health, exercise auth endpoints, and confirm rendering in a real browser), and when a defect is claimed, pinpoint the first failing request/state transition before implementing anything. Confidence: 0.7
- When verifying visual behavior in a real browser, sets theme mode via the app's own mechanism (e.g., localStorage key + reload through the app's ThemeScript) and verifies the DOM root state (`data-theme`, `.dark` class) AND resolved CSS custom property values together, since a class can be present while the cascade still applies the wrong palette. Confidence: 0.7
- Deliverable style depends on task type: for engineering wave work expects a written report file (e.g., `CODEX_WAVE4_ENGINEERING_REPORT.md`); for debugging/fix tasks explicitly wants NO reports, documentation, TODOs, markdown files, release notes, or speculative improvements — return only root cause, exact failure point (file/function/line), minimal fix applied, files modified, runtime verification, and remaining issues, then stop when done. Confidence: 0.8
- For visual/browser audit tasks, wants a scored result delivered in chat (no files): overall visual compliance score (0–100), screenshots as evidence, verified visual + computed-style differences, root cause category, files modified, minimal fix, before/after comparison, and remaining visual issues. Rendered pixels (screenshots) are the only acceptance criteria — the repository, DOM, and generated CSS are explicitly NOT accepted as evidence; expects per-screen 0–10 scoring across design categories (layout, typography, color, spacing, depth, composition, motion, accessibility, consistency, premium appearance). Confidence: 0.8
